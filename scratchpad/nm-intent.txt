WHY IT IS NOT A CODE REVIEW (this is the whole rationale, and reviewers reading only the diff will not know it): on 2026-08-02 two verification layers ran over the same code. The diff-reading review layer found five real code defects. The hands-on dogfood layer, which had no diff and no implementation context, found the two failures that actually mattered - one app presenting FABRICATED AI output to a live account as if real, and another's flagship import producing an empty "Untitled Recipe" behind a beautiful, finished-looking review screen. Neither was a code defect; the code did exactly what it was written to do. Independence from the implementation is therefore the load-bearing property of this whole feature, and most design decisions below exist to protect it.

DELIBERATE DECISIONS AND TRADEOFFS (all intentional; please do not flag these as mistakes):

- The verifier is handed ONLY a bare commit id and the user-facing promise. It is NEVER given the branch name, because fm/<task-id> identifies the implementing task and is a direct thread back to its brief, report, and PR. This is why fm-verify resolves a SHA and passes FM_VERIFY_REV rather than passing a ref name through.
- --promise / --promise-file is MANDATORY and is never defaulted from the task title, brief, or commit subject. Defaulting it would feed the verifier the builder's own framing, which is the exact contamination the role exists to avoid. The refusal is intentional UX, not an oversight.
- The verifier spawns as a SCOUT (fm-spawn.sh --scout) rather than introducing a new kind=verify. Scout semantics (scratch worktree, report deliverable, no branch, no push, no PR) are already exactly a verification's shape, so reusing them avoids threading a new task kind through fm-spawn, fm-teardown, fm-crew-state, fm-fleet-snapshot and fm-bearings-snapshot for no behavioral gain. Provenance that scout alone cannot express is carried by a small private sidecar, state/<verify-id>.verify.
- fm-verify.sh deliberately does NOT build the app, even though the captain's spec sentence said "builds the app". Build commands are project-specific and routinely run for many minutes; a spawn command that blocked on xcodebuild would be wrong. The generated brief makes the build the verifier's FIRST step after checkout, from the project's own documented build path, and treats a build failure as a verification RESULT ("not delivered - does not build") rather than a blocker. This reasoning is recorded in the script header.
- COMPOSITION over duplication was an explicit constraint: worktree allocation, harness/model/effort resolution, runtime backend selection, endpoint creation, turn-end hook wiring and metadata publication all stay in bin/fm-spawn.sh, which fm-verify.sh calls as a real subprocess. fm-verify owns only what scout spawning has no notion of: revision resolution, refusals, binding, and capacity.
- TRIGGER RULE: the captain proposed "any change a user could notice gets verified; internal-only changes do not" and explicitly invited a better argument. I inverted it, because "could a user notice?" invites "would they REALLY notice?" and degrades to "skip it when busy". AGENTS.md now states verify-by-default with a CLOSED exemption list (refactors with no behavior change, test-only, documentation, build or CI tooling, comments), mixed changes are verified, and a skip must name its list entry. This wording choice is deliberate.
- CAPACITY: FM_VERIFY_MAX_CONCURRENT (default 2) reflects the box capping at ~2-3 simulator jobs. Hitting the cap REFUSES with a message stating the verification waits; there is deliberately NO exemption path, because an exemption is how the role would become decorative. A refusal (exit 1) is the intended behavior here, not a failure mode.
- ANTI-"ALWAYS SAYS DELIVERED" DEFENCES, per the captain's explicit request: the brief requires specific per-claim evidence (screenshot or named observed behaviour), bans "looks good"/"works as expected"/"no issues found" as evidence, caps the verdict at "partially delivered" whenever ANY claim went untested, and requires both a "Looks finished but is not" section and a "What I could not test, and why" section, plus an independence attestation.
- KNOWN ACCEPTED LIMIT, documented in the script header rather than hidden: the default verifier id is <ship-id>-verify, so the ship task's id does reach the verifier through its own status/report paths. Firstmate must be able to see at a glance which merge a verdict gates, and an opaque id would cost more in operability than this leaks in independence. --verify-id closes it when independence matters more. AGENTS.md's wording was deliberately corrected to NOT claim the task id is withheld, so the stated rule matches what the tool actually does.
- SCOPE CALL, deliberately left out: a "not delivered" verdict blocks the merge as a POLICY gate in AGENTS.md, not as a hard refusal inside bin/fm-pr-merge.sh. fm-pr-merge is load-bearing for every merge in the fleet, no existing task carries a verdict yet, and a structural refusal would require encoding the trigger rule in a script. Flagged to the captain as the obvious follow-up rather than smuggled into this change.
- FM_VERIFY_SPAWN_OVERRIDE is a documented integration/test seam, consistent with this repo's pervasive FM_*_OVERRIDE testing culture (FM_ROOT_OVERRIDE, FM_STATE_OVERRIDE, FM_DATA_OVERRIDE, FM_PROJECTS_OVERRIDE, FM_CONFIG_OVERRIDE). It is what lets the tests assert real spawn arguments and rollback behavior without allocating worktrees or endpoints.
- fm-brief.sh now refuses combinations of --scout/--verify/--secondmate instead of letting flag order silently pick one, because each kind carries a different safety contract.

CONSTRAINTS HONOURED: stock bash 3.2 (both scripts and both suites verified under /bin/bash 3.2.57); shellcheck clean via bin/fm-lint.sh; simulator hygiene (shut down AND delete, report counts, remaining must be zero) is a standing captain order and is in the brief template; firstmate-coding-guidelines was loaded before touching shared tracked material, so mechanics live in script headers/--help and only the always-needed contract went into AGENTS.md.

- The verifier launches OUTSIDE any repository, against a built artifact copied to a neutral directory, so no harness can autoload project AGENTS.md/CLAUDE.md. This replaced an earlier "suppress autoload" approach, which the captain rejected.
- One narrow neutral launch mode was added to bin/fm-spawn.sh. The pre-existing broken validate_spawn_worktree is deliberately NOT fixed here; it is filed separately as fm-spawn-isolation-guard-fails.

- The "not delivered blocks the merge" rule is a POLICY gate in AGENTS.md; a hard refusal inside bin/fm-pr-merge.sh was deliberately excluded and flagged as follow-up.
- Machinery never speaks for the product: every orchestration/infrastructure failure (worktree allocation, runner start, copy, unconfirmed cleanup, symlink escape, build timeout) reports blocked/error and NEVER writes a product verdict. Only a build command that actually ran and failed yields a product result.
- Containment of build descendants is best-effort by construction on macOS (no cgroups, no PID namespaces). The deliberate contract is to FAIL CLOSED and refuse rather than acquire non-cooperative process tracking; building a process supervisor (kqueue/dtrace/eBPF/compiled helper) was explicitly ruled out of scope.
- After the eighth round, six residual auto-fix findings in the build-runner orchestration were deliberately ACCEPTED and are to be filed as a scoped follow-up ("fm-verify build-runner hardening"): detached-daemon cwd escape, tmux/cmux endpoint-identity confirmation, and compound cleanup-publication failure cases.
